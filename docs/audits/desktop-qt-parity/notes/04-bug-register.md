# Caderno Qt Bug Register

Findings are based on source inspection of the active worktree. Severity is based on content integrity and the normal user path. Fix status must be updated only after a source re-review and the corresponding focused verification.

## QT-NOTES-001: Filtering can save a filtered table projection

- **Severity:** High; possible silent content loss.
- **Evidence:** `apps/desktop-qt/qml/notes/NotesTableExcelGrips.qml`, `applyVisualFilterEvaluation()` assigns filtered HTML to `textEditor.text`. `apps/desktop-qt/qml/notes/NotesRichTextInput.qml`, `onTextChanged`, marks ordinary text changes pending and restarts the commit timer. `NotesRichTextEditor.qml`, `commitEditorText()`, serializes the live `QTextDocument` back to `sourceHtml`.
- **Reproduction:** Open a note with a table, filter out one or more rows, then wait for autosave or trigger a save/navigation path before clearing the filter. Reopen the note and check whether hidden rows remain. Editing while a filter is active also risks serializing only visible rows.
- **Root cause:** A presentation-only filtered projection is written into the same document model and commit lifecycle used for canonical edits.
- **Required fix:** Make filtered HTML an explicitly read-only projection; suppress dirty tracking for programmatic projection swaps; restore the original unfiltered document on clear or page change. Project only the selected table in Core.
- **Acceptance:** Filtering never changes saved source; save/close/reload while a filter is active retains all original rows; filtering a second table affects only that table; visible rows and table schema match React.
- **Fix status:** Source fix applied in `NotesTableExcelGrips.qml`, `NotesRichTextInput.qml`, and `NotesRichTextEditor.qml`. The projection is read-only, suppressed from dirty tracking, and generated by a table-indexed Core function. Save, navigation, and reload acceptance still needs runtime verification.

## QT-NOTES-002: Dropped files create unresolvable attachments

- **Severity:** High; the inserted attachment cannot resolve to stored file content.
- **Evidence:** `apps/desktop-qt/qml/notes/Editor.qml` drop handler inserts `data-type="file-widget"` with `fileName` and `fileUrl`. `FileAttachmentWidget.qml` resolves a file via canonical `data-file-id`/`fileId`, and previews only when a Core file ID exists. `NotesMediaWidgetPickerModal.qml` already uses `importLocalFile()` and inserts canonical `data-file-id`, `data-name`, `data-file-name`, `data-file-type`, and `data-file-size` attributes after import.
- **Reproduction:** Drag a non-image file from the OS onto a note and click the resulting card. The card has no file ID and no registered encrypted file to preview.
- **Root cause:** The editor bypasses the file import/persistence pipeline and writes raw path-like attributes that are not part of the React-compatible file widget schema.
- **Required fix:** Route local dropped files through the same encrypted import flow as the picker; after a successful import, insert the returned Core file ID and canonical metadata. Reject non-local URLs safely. Handle multiple files in a serialized queue because the controller permits one file operation at a time. Surface failure and cancellation without inserting a broken widget.
- **Acceptance:** Local drops produce valid file records and canonical widgets; reopen/preview/export/delete/rename work; failed/locked imports add no widget; image drops continue through image import; multiple-file order is stable. If the target block changes during asynchronous import, do not attach at a stale cursor offset.
- **Fix status:** Source fix applied: dropped local non-image files now use the encrypted import pipeline, request IDs, a serial queue, canonical file widget attributes, and a captured source offset. The target rich editor is flushed before capture; the canonical block HTML is checked again after import, so edits during import abort insertion with feedback instead of using a stale offset. The insertion helper reports failure when serialization or parsing is unavailable, parsing produces no widget, or pending editor changes cannot be flushed; the UI reports that the imported files were not attached. QML signal ordering, multi-file order, vault lock handling, and reopen/preview acceptance remain unverified.

## QT-NOTES-003: Rich HTML split uses a different character unit than Qt

- **Severity:** High; insertion can split text at the wrong position.
- **Evidence:** `BlockListEditor.qml` passes a cursor position from the transformed Qt `TextDocument` to `controller.splitRichHtml()`. Qt positions are UTF-16 code-unit offsets. The previous Core scanner counted a supplementary emoji as one Rust scalar and skipped rendered paragraph/void-element positions. Page references are now converted to one-character native Qt objects to match the canonical Core atom offset.
- **Reproduction:** Type `A😀B`, put the caret after the emoji, invoke a slash widget command, and inspect the split/inserted HTML and caret.
- **Root cause:** The FFI contract does not state its offset unit; Qt and Rust use different string indexing units.
- **Required fix:** Define the Core split API offset as UTF-16 code units and map HTML character references, text, modeled block boundaries, line breaks, inline objects and React inline atoms to balanced source fragments. Convert Qt-only display transformations back to canonical source offsets in the native adapter. Keep the Core splitter focused in `block_ast/cursor_split.rs` and share HTML5 character-reference decoding with Notes parsing.
- **Acceptance:** Insert at caret boundaries around BMP and supplementary characters, combining marks, adjacent paragraphs/headings/list items/table cells, `<br>`, images, page references, named/numeric references, nested marks and tag attributes without loss, duplication, invalid HTML, or cursor drift. Check offsets against actual Qt `QTextDocument` positions for active/deleted reference objects and adjacent references; the preparation-only word joiner must not remain in or count as document content.
- **Fix status:** Source fix applied across Core and Qt: Core counts UTF-16 units, modeled block separators, `<br>`/inline objects and each canonical page-reference atom; the Qt adapter groups contiguous fragments of one page-reference anchor and maps the rendered label and its display-only boundary character back to the atom offset. Asynchronous file drops capture that canonical offset and reject attachment if the target block HTML changes. Balanced markup and HTML5 character references are handled. Core and desktop builds pass; actual Qt table/cell, object, break, paragraph and page-reference cursor positions still require runtime acceptance before closure.

## QT-NOTES-004: Block colors are not round-trip safe

- **Required fix:** Match React's semantic text color/highlight marks for the block action. Keep the Core style/color allowlists narrow and do not retain arbitrary CSS.
- **Acceptance:** Color and highlight survive Qt save/reopen and React round-trip; clear/reset matches React; unsafe CSS is rejected.

## QT-NOTES-005: Table filtering targets the first table but strips rows from every table

- **Severity:** High; incorrect filter output and risk of collateral edits.
- **Evidence:** `evaluate_table_filter()` in Core derives column types from the given fragment's table parsing; the Qt caller passes the entire rich HTML. `TableGripsHelpers.js:filterTableRowsHtml()` applies one shared row index to every `<tr>` in the whole fragment. `NotesTextOperations::richTableGeometry()` reports the active table geometry but no table identity/index.
- **Reproduction:** Put two tables in one rich-text slice with different row counts, focus the second table, and filter a value that matches one row. Observe which table is evaluated and which rows are hidden.
- **Root cause:** The filter contract is whole-fragment HTML with implicit first-table evaluation, while the UI action is scoped to the table under the caret.
- **Required fix:** Carry active table index through the bridge and make Core parse/evaluate/project only that table. Keep the projection separate from canonical content. Use that index for schema, validation, movement and filtering.
- **Acceptance:** Filtering any table in a multi-table note affects only that table; headers, spans, schema and other tables remain byte-preserved.
- **Fix status:** Source fix applied: Qt rich-table geometry reports the active table index; Core bridge operations use it for column schema, validation, projection, row/column movement and width updates. Multi-table runtime acceptance remains unverified.

## QT-NOTES-006: Column changes can discard group or child metadata

- **Severity:** Medium; custom group or child metadata can be lost during drag, resize, or reorder.
- **Evidence:** `BlockDragDrop.js` rebuilds column wrappers in `serializeColumnsGroup()`. `NotesColumnLayout.qml` calls that serializer during resize, balance and reorder. React's `appendToGroupInTr()` retains group attributes and child attributes while redistributing widths equally.
- **Reproduction:** Add custom `data-*` attributes to a group/column, then resize, reorder, or drag another block into the group. Compare saved attributes and widths.
- **Root cause:** Qt regenerated every child wrapper from only its body and width and created a new group without the old attributes/ID.
- **Required fix:** Preserve existing group attributes/ID and child opening-tag attributes while updating width. When adding a column, redistribute widths equally to match React.
- **Acceptance:** Resize, reorder, and drop preserve all unrelated group/child attributes and content; widths follow React's equal redistribution on add; undo restores the previous structure.
- **Fix status:** Source fix applied: Qt retains the group attributes/ID and existing child opening tags across layout operations, updating only width and flex style. Static-source review passed; drag/resize/undo runtime acceptance remains unverified.

## QT-NOTES-007: HTML attribute decoding is incomplete for AST values

- **Severity:** Medium; uncommon entities can be rendered or reserialized literally.
- **Evidence:** `block_ast/helpers.rs::html_unescape()` decodes only `quot`, `#39`, `lt`, `gt`, and `amp`. Numeric references, non-breaking spaces and named entities may remain encoded when parser values are used by QML widgets or code.
- **Reproduction:** Load custom-widget attributes and text containing decimal/hex numeric entities, `&nbsp;`, and accented/supplementary characters; edit another block and save the page.
- **Root cause:** The parser's entity decoder was a small fixed replacement list.
- **Required fix:** Use a standards-compliant HTML entity decoder or a bounded decoder with a documented supported set. Avoid double-decoding and preserve literal unknown entities.
- **Acceptance:** HTML parse/serialize preserves rendered values and canonical escaping for supported named and numeric entities; malformed entities do not panic or corrupt neighboring attributes.
- **Fix status:** Source fix applied: Core now uses the HTML5 named-entity table, decodes decimal/hex references including HTML replacement rules, and uses separate text/attribute contexts to avoid ambiguous semicolonless decoding in attributes. Decoding remains one pass and unknown/malformed references stay literal. `cargo check` passes; parse/serialize cross-client round-trip acceptance is pending.

- **Acceptance:** Verify timestamps just before/at the −15 minute boundary, at start, at +60 minutes, after completion, after record deletion, and after a time-zone transition; the live animation/timer must stop when the delegate is destroyed.
- **Fix status:** Source fix applied in `CalendarEventWidgetState.qml` and `CalendarEventWidget.qml`. A one-shot timer schedules the next state boundary and the pill uses an amber pulse only while live. Runtime boundary, animation and lifecycle acceptance remain open.

## QT-NOTES-027: Recurring event widget deletion leaves orphaned occurrences

- **Severity:** Medium; deleting a linked widget can leave future events from its series in the agenda with no corresponding note widget.
- **Evidence:** The Qt `/evento` form supports recurring daily, weekly, monthly, and yearly series. Core marks each generated occurrence with a shared `recurrence_rule`, while the widget's delete path previously called only `deleteCalendarEvent(eventId)` for the first occurrence.
- **Reproduction:** Create a future recurring event from a note, confirm the widget deletion, and inspect the agenda for the remaining occurrences.
- **Root cause:** The widget removal flow treated a series-generated event like a standalone calendar record.
- **Required fix:** When an active linked event has a Core recurrence group, explain and delete the whole series through the existing typed controller/Core API. Keep expired-event behavior consistent with React by removing only the note widget and retaining the agenda data.
- **Acceptance:** Confirm cancellation leaves all occurrences and the widget unchanged; confirming deletion removes every active occurrence in the group and the widget; failed series deletion preserves the widget; expired linked events retain the series.
- **Fix status:** Source fix applied in `CalendarEventWidgetState.qml`; confirmation text now names full-series deletion and Core series deletion is used only for active recurring events. Runtime confirmation, failure, expiry and recurrence acceptance remain open.

## QT-NOTES-028: Unlinked event widget cannot be removed

- **Severity:** Low; older or imported event widgets without a Core event ID can become stuck in the note.
- **Evidence:** React's `deleteWidget()` deletes the linked event only when a record can be resolved, then always removes the note node after confirmation. Qt previously treated an empty event ID as an active linked event and failed deletion when no controller record existed.
- **Reproduction:** Open a legacy `calendar-event-widget` with no `data-event-id`, use its remove action, and confirm. The widget remains because no calendar record can be deleted.
- **Root cause:** The native confirmation path did not distinguish an unlinked widget from an existing or missing linked event.
- **Required fix:** Confirm removal of the note widget without calling Core when the event ID or event record is absent. Continue to show the distinct missing-record message when an ID exists but its record is gone.
- **Acceptance:** Confirming an unlinked widget removes only that node; cancellation preserves it; no calendar API is called; missing-linked and expired-linked behavior stays unchanged.
- **Fix status:** Source fix applied in `CalendarEventWidgetState.qml` using explicit linked-record state and a confirmation message for unlinked widgets. Runtime removal and cancellation acceptance remain open.

## QT-NOTES-029: Linked event widgets scan a capped calendar list

- **Severity:** Medium; many linked widgets repeat full-list reads, and events beyond the Core query limit can appear deleted.
- **Evidence:** `CalendarEventWidgetState.qml::syncFromCore()` previously called `getCalendarEvents()` and linearly scanned its result for each widget. Core `get_calendar_events()` sorts and limits the result to 300 rows, so an event outside that page was reported missing even when it existed.
- **Reproduction:** Create more than 300 calendar events and link a note widget to an event outside the returned page, or open a note with several linked event widgets and inspect repeated full-list lookups.
- **Root cause:** The widget used a list API for an identity lookup and had no focused change notification after Qt event mutations.
- **Required fix:** Add a typed event-by-ID Core/bridge/controller query and a dedicated Qt calendar mutation signal. Widgets should load only their linked record and refresh when relevant Qt calendar mutations succeed.
- **Acceptance:** An event outside the first 300 records resolves correctly; a note with multiple widgets performs one indexed identity lookup per widget rather than repeated 300-row scans; create/update/status/delete refreshes all visible linked widgets; failed mutations do not emit false refreshes.
- **Fix status:** Source fix applied through the existing Core ID query, `bridge-qt`, `SynapseDataController`, and `CalendarEventWidgetState.qml`. Release bridge/desktop builds and focused QML lint pass; runtime scale and synchronization acceptance remain open.

## QT-NOTES-030: Editing a native page-reference label can lose text

- **Severity:** High; editing the visible title can be discarded when Qt serializes the rich-text slice.
- **Evidence:** React renders `PageReference` as an atomic, non-editable node. The previous Qt editor expanded the canonical empty `span[data-page-id]` into an editable anchor label, then serialized the label back to an empty span. The current source converts that label into a one-character `QTextObjectInterface` object, with a native selection range and canonical serialization.
- **Reproduction (pre-fix):** Place the caret inside a native page-reference label, change or paste text, then save and reload the note. Compare the label and serialized `data-page-id` reference.
- **Root cause:** The previous native display used regular editable text for a React atom, and serialization did not validate that its label still matched the linked page.
- **Required fix:** Implement a native inline object with React-equivalent selection and deletion; preserve cursor-to-Core mapping as one canonical atom per reference; preserve React's canonical HTML at save and clipboard boundaries.
- **Acceptance:** Confirm at runtime that the object cannot be edited as ordinary text; Backspace/Delete, typing replacement, click preview/deleted notice, confirmed removal and undo match React; active and deleted objects serialize without losing content; emoji/combining text around objects maps correctly; save/reload and React↔Qt clipboard round-trip preserve page ID/title. Include React's ProseMirror clipboard wrappers and browser HTML fragment markers. Verify screen-reader label, focus, selection feedback and matched-viewport chip styling.
- **Fix status:** Source implementation applied in the native object handler, QML actions, clipboard adapters and serializer. Desktop and focused test binaries compile; no runtime tests or visual/accessibility review have been run. Status remains Partial pending acceptance above.

## QT-NOTES-031: Adjacent identical page references can be lost during serialization

- **Severity:** High; saving adjacent copies could fail or drop canonical reference markup.
- **Evidence:** `QTextDocument` can merge adjacent custom inline objects with identical character formats into one `QTextFragment`. The previous serializer required a reference fragment's text to equal exactly one object-replacement character, even when the fragment contained multiple identical adjacent objects.
- **Reproduction:** Copy/paste the same reference twice so the objects are adjacent, then serialize/save the note. Inspect whether both canonical spans are retained and can be reopened as separate references.
- **Root cause:** The serializer treated fragment boundaries as node boundaries, but Qt is allowed to coalesce same-format objects into one fragment.
- **Required fix:** Iterate every object-replacement character in a page-reference fragment and emit one canonical `span[data-page-id][title]` for each.
- **Acceptance:** Adjacent identical references, adjacent different references and references separated by text each serialize to the same count/order of canonical spans; Qt reopen and React round-trip retain every page ID/title; deletion and cursor selection still target exactly one object.
- **Fix status:** Source serializer fix applied and included in the desktop build. Runtime confirmation of Qt fragment coalescing and round-trip remains open.
